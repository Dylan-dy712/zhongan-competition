# 就诊人跨会话记忆：第一阶段实现

日期：2026-10-16。范围：普通关怀聊天、记忆管理和 Semantix BM25 检索；报告记忆引用仍保持原有发布门槛。

后续更新：发布分支已移植到最新主分支，迁移编号改为 028，并完成报告引用闭环及 029 报告授权开关；最新范围与验证见[第二阶段说明](patient-memory-reports.md)。以下保留第一阶段记录。

## 已实现的行为

- 记忆归属为登录账号 `actor_id` + 就诊人 `subject_id`；当前对象从会话及案件解析。即使两个账号都有同一主体的访问关系，也不共享私有聊天派生记忆。
- 每位就诊人独立开启 `continuous_care_memory`，与 `case_guidance` 分开。前端、后端及新数据库默认关闭回忆；迁移首次执行时清除旧 recall=true 的隐式开启状态，不自动把它升级为长期授权。
- 每个对话分别控制读入记忆与成为记忆来源。兼容的 `/recall` 端点只改变读入，不顺带打开来源导出。
- 候选需引用该账号、该就诊人、已完成用户消息中的原文，并由用户确认。助手回答、分析续答和改写文本不能直接成为长期记忆。
- 模型可提出少量沟通偏好、关怀偏好或过敏自述候选，服务端只保留与当前用户消息全文相同的内容；仍需用户确认。动态用药、恢复与复查自述由编辑器显式选择本次就医范围和有效期。
- 支持通过新来源更正已有版本、停止使用、过期和忽略候选。停止来源共享会撤回其派生有效记忆；重新开启来源或长期用途不自动恢复旧条目。
- 来源、用途、成员访问、版本、有效期在检索前、模型调用前和落盘前重新校验。中途更正或撤回时返回 `MEMORY_CONTEXT_CHANGED`，丢弃旧结果，保留可重试的用户消息。
- 旧回答的记忆依赖和显式历史检索依赖分别登记。依赖失效时隐藏其回答内容并排除后续模型上下文；增加无关新记忆不会使仍有效的旧回答消失。
- 当前对话的用户自述仍可在本次关怀授权内使用；跨会话自述不再由旧 `get_patient_context()` 自动旁路注入。

## 数据与检索

新增迁移 `023_patient_memory.sql`。PostgreSQL 保存设置、用途授权、候选、内容版本、幂等操作和回答引用；应用更正内容时追加新版本。案件与主体的复合外键补强就医范围一致性。

`memory_repository.py` 做业务授权和生命周期管理；`memory_service.py` 装配上下文并调用 `services/memory-ranker`。这不是把全部模型请求透明转发到通用网关。

Go 适配器直接使用 Semantix 提交 `5e546dcb69b7545e9fba9f95f9464c0ddd6f9cff` 的 BM25、CJK tokenizer 和相关值类型。上游源码与 MIT 声明随项目保存，保留原始 Git blob 标识及 SHA-256 清单；构建时校验，不需要在线下载 Go 模块。

每次调用通过 stdin 传入已获准的候选，创建请求内临时索引；stdout 仅返回不透明 ID 和分数。业务层使用 PG 正文重新装配，不接受检索器指定其他患者、路径或权限。进程不读取开发助手全局库、不持久化患者索引、不运行通用会话提取或 L3 回答复用。

首期限制：最多 256 条有效记忆、单条 1000 字、最多注入 5 条 / 2500 字；检索进程超时为 2 秒。中文匹配采用上游 BM25，相关性使用保守词汇覆盖和相对分数门槛。沟通偏好在范围匹配且来源有效时参与背景。上述是配置边界，不是语义质量或延迟收益证明。

检索器缺失、超时或协议异常时，当前聊天可继续，响应记录 `memory_status=retrieval_unavailable`。权限或医学安全验证失败不按检索故障降级放行。

## 前端使用

1. 在“我的”切换到对应就诊人，打开“关怀记忆”，单独开启长期用途。
2. 在聊天中打开“本对话的关怀记忆”，分别选择是否读入、是否允许来源。
3. 可以确认待保存候选，或在用户消息下选择原话作为来源。编辑器显示具体就诊人，提供范围、有效期和明确确认按钮。
4. 更正时选择新的来源消息，创建新版本；“停止使用”会关闭后续使用，界面不把它称为已物理删除原聊天或审计副本。

成员切换会卸载相应管理面板；异步读取检查生命周期，写入 URL 固定绑定打开时的就诊人。延迟返回的旧就诊人结果不能覆盖新面板。

## 本机启用与构建

先配置专用开发 PostgreSQL 连接串，按项目现有方式备份并迁移目标开发库；本轮只在临时验收库执行迁移，未更新线上业务库。

```powershell
python -m scripts.build_memory_ranker
python -m scripts.migrate_database
python -m uvicorn services.api.app.main:app --reload
```

构建需要 Go 1.26+；API 运行只需要构建后的检索器，不需要 Go。默认查找 `output_dir/memory-ranker/semantix-ranker.exe`（Windows）或 `semantix-ranker`（Linux）；也可用 `ZHONGAN_MEMORY_RANKER` 指定受控二进制的绝对路径。该环境变量不是 shell 命令，不能附带任意参数。

Linux CI 构建并测试检索器，使用 PostgreSQL 16 运行业务测试，并提供 `semantix-memory-ranker-linux-amd64` 构建产物。部署时需同时包含新 API、迁移、前端和检索器；不能只上传网页。CI 配置变更不等于远端 CI 已运行，也不表示线上已部署。

Pydantic 是记忆输入 / 输出契约来源，`python -m scripts.export_memory_contracts` 生成 `contracts/memory.schema.json` 和前端类型。

## 当前边界

第一阶段实现 `communication_preference` 和 `confirmed_context`；`care_plan_ref` 与报告生成 / 审核 / 发布的记忆闭环留在第二阶段。材料解读过滤依赖长期记忆的旧回答，报告端原有非空 `memory_refs` 拦截保留。

尚未接入模型嵌入、个性化医疗回答 L3 直返、真实医疗数据、自动处方承接、物理删除调度或记忆效果收益评测。长期自述的确认不能替代临床核实。

并发撤回的模型调用在事务外执行，最终快照核验和更正 / 撤回操作通过共同的账号＋就诊人锁排序；最终保存同时锁定目标对话的关怀用途、成员访问和账号状态，来源校验锁定对应来源授权。已经发给模型或已经送达的内容不承诺追回。
