# 医疗服务引导与推荐验收

2026-10-16。需求见 `docs/requirements/medical-service-guidance.md`。发布副本基于线上 main `2d55f5d` 单独移植，保留当前完整解读、逐句引用和批量补问逻辑。

## 实现

- 材料解读及已发布报告末尾加入暖暖形象、温和邀请和三个快捷提问按钮；沿用发送逻辑，保留输入草稿和附件，忙碌时禁用。
- 普通对话通过原生工具 `recommend_medical_services` 选择权益、线下机构和互联网医院，不用关键词固定回复。模型结合当前问题和当前对话上下文，选择一类或组合。
- 工具读取 `contracts/medical-services/catalog.json`：8 类服务，309 条医院网络成员/公立资料记录（含不同产品重复成员，不是309家独立合作医院）。源数据由本轮调研导出，运行时不依赖 output_dir。公立官网地址和私立保险名单分别注明来源；部分私立地址有独立医院官网佐证。
- 中高端权益是演示前提，未伪造真实保单查询。体检四选一、绿通的约定疾病/等待期、购药加油包、使用次数等限制随卡片展示。
- 普通复查不推荐肿瘤/康复专病机构；专科需求可筛选相应机构。复查不自动替换为体检。需要线下评估时抑制线上/体检卡；急症工具状态只显示急救承接，且不能被后续工具调用降级。
- 地点须逐字来自本对话用户消息，缺城市或区县重名时追问。地区匹配使用同城及地址片段，没有坐标或真实距离；没有匹配时说明名录缺口，不跨城凑名单。
- 卡片提供条件/来源折叠区和可点击模拟入口；弹窗展示服务步骤，可继续让暖暖协助准备。没有真实预约、支付、问诊或医疗资料传送。
- 卡片是服务器生成的回答元数据，随既有 JSON 回答保存，无新增数据库迁移；重开历史可展示。卡片不会重新塞回模型历史上下文；旧位置表单不再交互。

## 验证

发布副本运行 `python -m unittest tests.test_medical_services tests.test_conversation_agent tests.test_patient_followup`：52 项，50 项通过、2 项因未配置专用数据库而跳过。新医疗服务测试13项全部通过，覆盖原生工具循环、地区来源、绿通条件、体检互斥、公私立偏好、专病过滤、急症及报告独立元数据。数据库及 Linux 部署测试交由发布 CI 完整验证。

在 `apps/web` 运行 `node scripts/check-medical-services.mjs` 与 `node scripts/check-chat-followups.mjs`：通过。使用实际 App 组件和后端生成的合成卡片，覆盖报告入口、草稿/忙碌保护、三类模拟弹窗、地区输入重试、历史恢复及准备事项追问。

`tsc --noEmit` 和 `vite build` 通过。真实浏览器检查桌面及390×844手机视口：单列卡片、弹窗滚动及模拟入口可用，页面无横向溢出。截图保存在 `output_dir/medical-service-feature-20261016/`，均为合成展示内容。

模型循环由脚本模型验证，本机未配置 LLM 运行环境，尚未完成真实模型的多轮语义回归；数据库集成跳过项也不计为通过。当前功能未验证实时号源、个人保险资格、机构实时合作状态或预约闭环。

## 发布要求

`contracts/medical-services/` 已纳入提交打包白名单、运行时差异比较及新安装/更新复制。发布时先备份，加载目录确认非空，再启动服务；增加仅目录变化也必须重新启动运行时的 Linux 部署测试。前端测试使用实际后端目录生成合成卡片，web CI 显式安装同版 Pydantic。

按现有流程：PR CI 通过后合并，等确切 main push CI 成功，下载并校验该次构建产物，再部署和验证远端版本、代码/目录哈希、服务及公开静态资源。真实模型合成验证与线上读回记录另存本地发布证据，不将其视为医学效果评测。
