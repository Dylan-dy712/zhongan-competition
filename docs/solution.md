## 1. 问题与产品主张

**用户痛点**：理赔后的患者拿到的是一堆专业文书——不知道自己经历了什么、费用花在哪、下一步该做什么；保险公司只完成赔付，错失了服务时点。

**产品主张（理赔即关怀）**：以理赔材料为唯一事实入口，在赔付完成的时点自动生成"你能看懂的本次就医全景报告"，并基于真实历史数据提供有限度、可解释的下次就医参考。服务闭环：`理赔触发 → 病历结构化 → 痛点识别 → 温度指引 → 品质画像与推荐 → 触达与反馈回流`。

**明确不做**：不替代诊断/处方、不自动改变理赔结论、不宣称机构绝对优劣、不自动预约。

## 2. 总体架构

```
┌─────────── 数据层（仓库外，合规隔离）───────────┐
│ 脱敏扫描件 (work/dataset) │ OCR 文本+坐标 (work/ocr) │ 捆束 (work/bundles) │ 运行产物 (work/runs) │
└──────────────────────────────────────────────────┘
        │ scripts/batch_ocr.py（RapidOCR，729页/90min/6进程，0 失败）
        ▼
┌─────────── 流水线（services/api/app/pipelines）───────────┐
│ 1 doc_classify  内容判别文档类型（不信文件名），标题区加权       │
│ 2 extract       确定性规则抽取五类字段 + 证据 + 置信度           │
│ 3 insights      六类候选痛点（临床2/费用2/体验2），judgment/review 分离 │
│ 4 guidance      LLM 六段式温度报告（事实摘要+知识包注入），确定性校验 │
│ 5 profile       医院×病种五维画像快照（分子/分母可复算）          │
│ 6 recommend     可解释推荐 / 样本不足明确拒排                    │
│ 7 validate      证据引用存在性、日期序、金额非负、六段完整性        │
└──────────────────────────────────────────────────┘
        ▼  scripts/run_offline.py（批量）/ app.main.py（FastAPI + 演示前端）
```

**AI 原生度构成**（对应红线检查）：医疗文档结构化理解（页级分类+字段抽取+证据定位）、NLP 痛点挖掘（规则层可复算 + 语义层候选）、LLM 个性化温度生成（事实锚定 prompt + 结构化输出 + 校验）、多维画像建模（可复算指标）、可解释推荐（理由引用快照指标）。

## 3. 关键技术设计

### 3.1 OCR 与文档理解

- **引擎**：RapidOCR（onnxruntime，CPU）。选型理由：离线可跑（医疗数据不出内网的可选路径）、中文强、零调用成本；生产可平滑替换为 AI 中台 OCR（接口已按"页文本+行坐标+置信度"抽象，坐标按 spec §5.3 归一化）。
- **工程要点（踩坑实录）**：Windows 中文路径需 `np.fromfile+imdecode`；多进程池与 onnxruntime 在 win32 死锁，改分片独立进程（6 片 90 分钟跑完 729 页，0 失败）。
- **文档类型判别**：加权关键词规则 + **标题区（前5行）双倍权重**。动机：出院小结正文页满是"检验报告"字样会被误判；实测纠错案例——文件名"发票"实为病案首页（置信 0.86），UUID 命名的手机截图按内容区分出门诊病历/检验单。输出类型+置信度+命中特征，供下游选择抽取策略。

### 3.2 结构化抽取（KR1）

**两层方法**：

- **A 层（确定性规则，当前主实现）**：针对结构化文书的高精度模式。已验证的关键规则：
  - 日期：行内优先→标题行下方 2 行兜底；**OCR 吞世纪位修复**（"5年10月27日" → 用同页完整日期后缀推断 2025）；住院锚点优先、门诊锚点（就诊/检查/报告日期）兜底；
  - 住院天数：原文优先，否则推导（出院-入院，同日计1），**>400 天判冲突不出值**（防日期错误传导）；
  - 手术：病程叙述句式（"于X日全麻下行XXX术"）+ 病案首页表格**跨行断裂合并**（"单孔VATS左肺上叶部分"+"切除术"）+ 碎片子串去重；
  - 诊断：标题行内联 + 后续行双形态；病理/临床/门诊诊断角色化；【】部位前缀剥离；噪声段过滤（"具体见石蜡报告"）；
  - 费用：病案首页三口径（总/自付/自费）、医保结算单（统筹/个人）、电子票据"合计"兜底，金额统一转分、容忍 OCR 空格与全角逗号。
- **B 层（LLM 辅助抽取，已实现）**：`extract_llm.py` 每案 1 次调用，从 OCR 全文抽诊断/药品/手术候选，**每条候选必须带原文引用且锚定回页/行**（锚定失败即丢弃，无证据不成候选）；计费页（费用清单/发票）候选一律不采纳——费用行出现的药名不代表处方。与 A 层合并：相似度 ≥0.75 视为重复、A 层保留，冲突时 A 层优先（确定性 > 生成性）。15 案内部金标实测：micro F1 0.574（纯 A 层）→ **0.687**（A+B），召回 0.533→0.808；单案成本 <1 分钱（glm-4.5-flash，约 9K tokens）。距官方 0.90 仍需逼近，后续路径：人工复核队列兜底 + B 层负面约束迭代 + 官方口径确认。

**每条值携带**：原值/规范值/状态（observed/derived/missing/conflict）/证据（文档+页+行+文本跨度+bbox）/置信度（规则强度×OCR 行分加权，未校准仅作排序）/方法版本。覆盖率（70 案内部口径）：医院 92%、诊断 80%、入出院日期 70%/61%、总费用 40%（其余为材料本身无该文书）、药品 25%。

### 3.3 痛点识别（KR2）

六类候选标签（映射赛题示例：用药与诊断不匹配→CLIN_MEDICATION_CONTEXT_REVIEW；非必要检查→CLIN_EXAM_JUSTIFICATION_REVIEW；自费比例异常→COST_SELF_PAY_DEVIATION；诊断术语晦涩→EXP_TERMINOLOGY_BARRIER；出院小结缺乏康复指导→EXP_DISCHARGE_GUIDANCE_GAP；另加总额/明细核对→COST_AMOUNT_RECONCILIATION）。

**设计原则**：
- 确定性规则可复算（分子/分母/阈值版本化），LLM 只做候选补充与话术润色，**不裁决严重度**；
- `judgment_status`（证据判断）与 `review_status`（人工审核）分离；临床类一律输出"需核实线索"，**禁止**在患者端表述为确定的误诊/错误用药；
- 无可比基准时自付偏离标 `indeterminate` 而非异常（spec §6.2）；
- 证据溯源：每条洞察挂 OCR 原文行，前端可回跳。

### 3.4 温度指引生成（KR3）

**Prompt 架构**（`guidance.py`，版本化 guidance-0.2.0）：系统提示词（写作七条军规：事实只来自病例摘要/承接具体经历/不过度保证/不下诊断/金额口径声明/知识包内解释/行动可执行）+ 结构化输入（事实摘要 + 病种知识包 + 痛点 + 用户关注点）+ 强制 JSON 输出（六段+行动+声明）。

**温度感的可度量实现**：承接经历（引用本次具体术式/天数/等待病理的处境）、尊重不确定性（待石蜡报告→"等待结果的时间确实难熬"而非空话）、行动有执行者与时间（due_at 无依据时为 null 并给确认路径）。配对测试用例：同病种仅改医嘱/关注点→相关段落变化、无关事实不变（QG-03）。

**实测样例**（glm-4.5-flash，单案 929+1164 tokens ≈ ¥0.001 级）：见 §7 演示。已知待修：心理安抚段对"待石蜡确认"的良性表述过于确定——已列入校验层规则（事实边界检查：报告不得将待确认病理表述为确定结论）。

**降级策略**：LLM 不可用时确定性拼装（锚定事实但语言模板），前端明示"模板模式"，**不冒充 live**（红线）。

### 3.5 品质画像与推荐（KR4）

- 实体：医院×病种组（病种组由诊断/手术关键词映射 9 组，版本化知识包）；
- 五维指标（分子/分母/样本数/缺失率全留存，可独立复算）：同组费用中位数、自付比例、住院天数中位数、出院带药记录率、出院文书完整率——后两项明确标注"文档代理指标，不代表疗效"；
- 推荐理由 ≥2 条独立依据，每条引用快照指标；**样本 <5 或指标不可计算 → 拒绝排序**（ranking_allowed=false，展示描述性信息+局限）；无综合质量分、无 LLM 口碑。

| KR2 | `evals/kr2.py` | 案件×标签机会一致率 + 标签级 P/R/F1 + 严重度一致 | 待金标 |

金标方案：`scripts/eval_cli.py gold-template` 生成机器预填模板（含预测值供核对），人工对照 OCR 原文修正——每案 10-15 分钟；计划 15-20 案（内部口径，不冒充官方标注）。

## 5. 数据合规与授权路径

- **用途模型**：case_guidance（单次关怀）/ resource_matching / continuous_care_memory / evaluation_reuse 四用途独立授权、独立撤回；理赔处理依据不自动覆盖二次用途（PIPL §13-14、28-30）。
- **脱敏边界**：官方数据已做人名掩码（manifest 含 bbox，可用于二次校验）；"脱敏≠匿名"，去标识化数据仍按个人信息处理；生产部署路径为内网/私有化推理，模型供应方处理范围需在委托协议中固定。
- **原型纪律**（已执行）：医疗图像与 OCR 产物全部在仓库外 `work/`；仓库内测试只用合成夹具；`.env` 密钥 gitignore；日志不落病历正文。
- **演示数据说明**：演示环境使用官方脱敏样例，报告输出含"脱敏样例"标识。

## 6. 工程架构与上线计划

**原型现状**：单 API 服务（FastAPI）+ 文件产物（runs JSON）+ 离线批处理 CLI + 静态演示前端；15 项单测全绿（合成夹具）；部署脚本 `deploy/setup_server.sh`（Ubuntu 一键）。

**生产化路径**（按 spec §4 演进，均为配置替换而非重写）：
1. 文件产物 → PostgreSQL（SQLAlchemy 兼容层已按关系+JSONB 语义设计，见 ADR-001）；
2. 同步执行 → 任务表+工作进程（Run 状态机已按 spec §7.1 定义）；
3. 触达：APP 推送/企微/短信适配（通知仅含服务提醒不含诊断详情，spec §8.4）；
4. 复核工作台：Insight 的 pending 队列 + 版本化 Report。

**资源估算**（内部实测口径）：
- OCR：RapidOCR CPU 6 进程 ≈ 8s/页；单案均值 10.4 页 ≈ 90s/案。生产 GPU 实例可降至 ~1s/页。
- LLM：指引生成 1 call/案 ≈ 2.1K tokens（glm-4.5-flash），70 案全量 < ¥0.2。抽取 B 层/痛点语义层增补后预算 ×5 仍 < ¥1/案量级。
- 全量 70 案端到端（含 LLM）< 1 小时单机。

## 8. 创新点

1. **"温度"的可度量**：六段式结构 + 事实锚定声明（claims 分型：case_fact/professional_explanation/to_confirm）+ 盲评锚点量表，温度从玄学变成可验证输出。
2. **确定性优先的信任架构**：能用规则复算的不用生成模型（费用/日期/画像），LLM 集中在语言与语义弹性区，每层带证据与版本——医疗场景的可解释与可审计优先。
3. **异常免疫设计（演化性）**：OCR 损坏检测（世纪位推断/冲突状态而非猜值）、画像样本门槛与扰动拒排、文档类型与病种组均为版本化知识包可热替换——病种分布漂移时更新知识包而非重训。
4. **长期健康管理延伸（加分项规划）**：复诊提醒（due_at 医嘱口径）→ 慢病随访计划（Memory 契约已定义 continuous_care 用途与撤回语义）→ 用药依从性（出院带药 + 行动状态跟踪）。

## 9. 风险与限制（如实）

- KR1 覆盖率受材料本身限制（部分案件仅有检验单，无费用/药品文书）——缺失按状态上报，不编造；
- 痛点规则的阈值（重复检查次数、自付偏离幅度）为候选值，需专家标注回归后冻结；
- 医学知识包为编写版候选内容，正式版需获准知识库替换；
- 盲评尚未执行；所有"内部口径"指标待金标后出数。
