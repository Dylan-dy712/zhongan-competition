# 众安·暖愈智护：Agent 协同开发详细执行方案 V3

> 团队讨论与执行手册 · 2026-09-22
> 适用方式：同学负责产品、数据、医学核验和集成决策，开发 Agent 并行实现，评审 Agent 独立检查。
> 本版取代 V1/V2 的开发分工与排期，保留五项官方 KR 和证据要求。所有目标、工时、技术选择均为计划；文中的目录、接口和脚本是待建设约定，不代表已经实现。

## 0. 先读这一页：我们最终要交付什么

我们要交付一个真实运行的“理赔后关怀工作台”：导入获授权的医疗材料，生成医疗时间线和有原文依据的痛点，给出个性化就医说明与下一步行动；有足够数据时给出医疗资源匹配；经用户同意记住表达偏好和关怀计划，下一次服务可以接续。

产品最终必须能现场完成以下操作：

1. 选择或上传一个病例，显示材料来源与授权状态。
2. 解析出诊断、手术、用药、住院天数和费用构成，字段缺失与冲突清楚可见。
3. 点击结构化字段，打开对应原文页或文本位置。
4. 展示临床、费用、体验三类痛点，每条含严重度、证据与下一步动作。
5. 生成六部分关怀内容：诊断通俗解释、治疗回顾、费用解释、康复计划、心理安抚、下次就医建议。
6. 展示至少五维资源画像和每项不少于两条的数据化匹配理由。
7. 把需要医生核实的内容送入复核流程，复核前不伪装为确定结论。
8. 收集用户对具体报告和行动的反馈。
9. 用户明确同意后保存偏好或计划引用，在下一次服务中使用；撤回后停止使用。
10. 展示真实评测结果、失败比例、调用成本、版本和降级方式。

**开发节奏：第一天建立统一契约，第二天完成纵向原型，第三天接通真实模型，第五天完成五项 KR 的功能路径，第七天完成可演示全链路，之后集中优化指标与准备答辩。** 数据和专家尚未到位时继续工程工作，但相关结果标为“未验证”。

Agent 写代码更快，因此不沿用纯手工开发的人时推算。我们采用“小任务、明确目录、并行实现、频繁集成”的方式；保留 25% 左右日历时间处理模型质量、数据变化和评审反馈。速度提升需要用前两个工作日的实际交付校准，不预设固定倍数。

## 1. 使用本手册的方法

1. 队长阅读第 2～5 节，确定人员、角色和统一约定。
2. 先执行 T00～T05，取得可用仓库、数据盘点和协议。
3. 按第 6 节的依赖顺序派发任务，不把整份手册当成单个 Agent 的无限任务。
4. 每次派工使用配套的《Agent 任务派发与验收手册》，加上对应任务卡。
5. 每个 Agent 提交代码、执行证据和未解决事项；由负责同学验收。
6. 每日按第 8 节检查里程碑；任何一天都应有可启动的主分支版本。
7. 指标与最终交付按第 9～12 节执行。

文中“开发 Agent”指帮助团队写代码的工具；产品本身不要求堆叠多个运行时智能体。产品主链路先用可观测、可重试的确定工作流完成。

## 2. 明确目标、数据依赖和优先级

### 2.1 五项 KR

- KR1：官方要求关键字段 F1 ≥ 0.90、缺失率 < 5%、JSON Schema 和字段级置信度。内部争取 F1 ≥ 0.94、缺失率 ≤ 3%。正式平均方式、匹配规则按赛方口径确认。
- KR2：覆盖三类痛点且至少五类具体标签，专家一致率 ≥ 85%；内部争取六至八类稳定标签、一致率 ≥ 90%。
- KR3：至少三个病种，每份包含六部分指引；温度感、可行动性分别 ≥ 4/5，内部争取分别 ≥ 4.5/5。
- KR4：画像 ≥ 五维，推荐 ≥ 两条理由，至少三病种且每病种五家机构。医院/医生/方案的交付粒度、跨病种机构可否重复向赛方确认。
- KR5：完整链路及理赔审核、客服工单、资源推荐系统对接方案，含明确授权与数据使用路径。

效果验证占 40%，完整性占 30%，落地性占 20%，创新性占 10%。开发 Agent 可以生成初稿和评测程序，不能把自评当专家标注、把合成结果当官方成绩。

### 2.2 三层范围

**必须完成：** 五项 KR；字段与结论证据；输入缺失/冲突处理；人工复核；真实模型路径；评测工具；一次偏好与计划的连续关怀；授权、隔离、撤回；报告与反馈；可恢复的演示环境。

**核心完成后争取：** 专家纠错经验检索、额外病种、异常版式监测、长期行动时间线、可读性切换、患者与工作人员双视角、消融实验扩充。

**不进入关键路径：** 从零训练大模型、复杂微服务、独立图数据库、复杂多智能体决策、真实短信/企微外发、大规模医生排名、未经验证的记忆自动进化。

“临床合理性”或“真实机构覆盖”没有数据支持时属于验收缺口，不能用功能按钮或模拟数据代替。拒绝无依据推荐是正确行为，但不会自动满足 KR4。

### 2.3 D1 必须向赛方确认

提交时间与形式；演示时长；指标计分方法；测试集与标注范围；医疗数据可用环境；是否允许外部模型；中台接口与额度；机构、医生及方案的字段；专家评审要求；官方知识与规则可用范围。

这些由队长实际对接，Agent 起草问题清单。没有答复的内容写入 `docs/decisions/open-questions.md`，不自行填成事实。

## 3. 同学和 Agent 如何协作

### 3.1 人员负责验收，而非包揽代码

- H1 队长/产品/评测管理员：确认需求与赛务，维护优先级、隐藏集和提交材料，批准共享契约。
- H2 数据/医疗协作：盘点材料、组织标注、联系医学审核者、验收结构化和痛点。医学资格不因担任这个角色而自动具备。
- H3 后端/模型集成：控制服务、数据模型、模型适配、Semantix 适配与版本。
- H4 前端/用户体验：验收页面流程、证据交互、阅读体验、演示环境。
- H5 QA/评测/答辩：组织自动测试、结果复现、盲评、故障演练和讲稿。若只有四人，H1/H5 合并；三人再合并 H3/H4，但限制同时验收的开发任务。

每项任务指定一名人类最终负责人。Agent 的“完成”只表示提交待验收，不等于团队接受。

### 3.2 Agent 工作角色

- A0 集成协调：维护依赖与接口变更、合并和每日基线。
- A1 契约与数据：Schema、样例、数据清单、标注格式。
- A2 文档理解：解析、OCR、字段抽取、事件及证据。
- A3 洞察与生成：痛点、事实计划、关怀输出与审核。
- A4 后端与记忆：权限、任务、存储、接口、Semantix。
- A5 画像推荐：统计、匹配、理由与数据质量。
- A6 前端：工作台、证据、报告、行动和管理入口。
- A7 独立测试：契约、端到端、回归、对抗和评测工具。
- A8 文档答辩：根据真实输出组织图文和答辩证据。

这些是任务角色，不要求同时打开九个 Agent。建议单个集成工作区先保持三至四个活动开发任务，按机器、额度及人工审查吞吐调整。评审积压时停止开新任务，优先合并已有结果。

### 3.3 并行开发的具体规则

1. 共享仓库以 `main` 为稳定基线。每个任务在独立分支和独立 checkout/worktree 执行；Git worktree 支持同仓库多个工作目录，适合隔离任务修改。[Git 官方说明](https://git-scm.com/docs/git-worktree)
2. 每个 Agent 读取同一版本需求、Schema、OpenAPI 和样例；记录起点提交。
3. 分配可写目录。Schema、数据库迁移、依赖锁文件、根配置由 A0 或指定唯一负责人合并，其他 Agent 先提变更请求。
4. 新能力需要改共享字段时，先提交契约差异和兼容方案，经 H1/H3 验收后更新版本，再通知消费方。
5. 每个任务建议一至两个 Agent 工作轮次完成；超过半天仍未有可运行结果时继续拆分。不得并行修改同一个任务文件来“抢进度”。
6. Agent 跑本模块测试后交独立评审，A0 基于最新主分支再跑集成检查。
7. 测试库、文件存储、端口、Semantix 数据库按工作区隔离，避免不同 Agent 互相污染。
8. 隐藏评测数据及标签不提供给开发 Agent；由受控评测执行器运行，开发只收到允许披露的结果。

### 3.4 一个任务的闭环

负责人填写任务卡 → Agent 复述输入与接口 → 编码并写针对性测试 → 输出差异与测试日志 → 独立 Agent 审阅 → 同学验收关键行为 → 集成合并 → 主流程冒烟 → 更新任务状态。

阻塞分三级处理：接口冲突交 A0；产品语义交 H1；医疗与数据使用判断交 H2/相应专家。Agent 不自行扩大数据用途或生成医学金标准。

## 4. 默认技术方案与目录约定

### 4.1 默认选型

尚无既定代码时，建议 React + TypeScript 前端，Python FastAPI + Pydantic 后端，PostgreSQL统一开发/验收数据库，服务端受控文件目录存材料，任务工作进程执行解析。组件版本在 T02 锁定，不在文档中猜最新版本。若团队已有稳定同类栈，可由 H3 在 D1 一次性替换，随后保持一致。

FastAPI 的 OpenAPI、JSON Schema 和输入验证可用于统一前后端契约，减少 Agent 各自猜字段。[FastAPI 官方说明](https://fastapi.tiangolo.com/features/)

第一版用数据库任务表加一个工作进程；避免只靠 HTTP 请求内长任务。存阶段状态、输入哈希、重试次数和错误码，重启后可恢复。先轮询任务进度，稳定后再考虑流式通知。

LLM/OCR 使用获准供应方的服务端适配器：`ModelProvider`、`DocumentParser`、`MemoryAdapter`。所有凭证从运行环境注入。知识检索先围绕小规模可审核材料，必要时再加向量索引。

### 4.2 建议仓库目录

```text
apps/web/src/
  features/cases/ evidence/ insights/ guidance/ recommendations/ memory/ review/
  api/generated/                 # 从契约生成，不手改
services/api/app/
  contracts/                     # Schema 唯一源，由契约负责人维护
  routes/ models/ repositories/   # API、业务存储与访问
  pipeline/                      # 阶段状态、作业执行与恢复
  modules/ingestion/ extraction/ evidence/ insights/
  modules/guidance/ recommendation/ memory/ review/
  adapters/                      # OCR、LLM、Semantix、模拟外部系统
services/api/tests/
contracts/                       # 导出的 JSON Schema、OpenAPI、样例
evals/                           # 指标与实验执行器，不含隐藏答案
tests/e2e/                       # 浏览器端端到端用例
fixtures/synthetic/              # 可公开的合成样例，带来源标签
infra/                           # 本地开发与演示配置
scripts/                         # 工程命令入口
docs/requirements/ decisions/ data/ medical/ privacy/
docs/tasks/ reviews/ evaluation/ demo/ delivery/
```

官方材料、真实患者信息、开发密钥、隐藏集均保存在授权的仓库外位置。`fixtures/synthetic` 不得悄悄替换成官方病历。每个任务卡中的路径是相对于未来仓库根目录的交付位置。

### 4.3 T02 要提供的统一命令

下面是命令接口要求，脚本需由 T02 创建后才可运行；不是当前已经存在的命令。

```powershell
# 检查环境，输出缺失配置但不打印凭证
pwsh -File scripts/doctor.ps1
# 启动隔离开发环境
pwsh -File scripts/dev.ps1
# 契约导出与兼容性检查
pwsh -File scripts/check.ps1 -Scope contracts
# 指定模块测试
pwsh -File scripts/check.ps1 -Scope extraction
# 前后端和集成检查
pwsh -File scripts/check.ps1 -Scope all
# 固定版本开发集评测
pwsh -File scripts/evaluate.ps1 -Split dev -RunId dev-001
# 端到端主流程
pwsh -File scripts/check.ps1 -Scope e2e
```

标准返回码：0 表示所选检查通过；其他值表示失败。日志记录输入版本和失败原因，不把“未执行”当成功。成本统计区分开发 Agent 调用与产品分析调用。

## 5. 所有模块共同遵守的数据契约

### 5.1 证据与事实

证据记录至少包含：`evidence_id, case_id, document_id, page_index, text_span, bbox, extraction_method, source_hash`。扫描件坐标统一为左上角原点和页面归一化坐标；文本材料没有几何坐标时用字符范围，不能编造 bbox。

结构化字段至少包含：`value, status, evidence_ids, confidence_score, confidence_method`。`status` 包含 `observed / derived / missing / unreadable / conflict / not_applicable`。推导值另存公式、输入证据和单位；确认的阴性、材料未提及、没有做某项操作不能混成一个值。

金额用十进制定点或最小货币单位，日期记录精度，住院天数使用官方定义并保留计算口径。可疑日期和跨页合计冲突不自动覆盖原值。置信分在校准前显示“分数”，不表述为正确概率。

### 5.2 痛点与行动

痛点记录：`insight_id, category, label, severity, confidence, evidence_ids, rationale, uncertainty, suggested_action, review_required, review_status, rule_version`。

行动记录：`action_id, report_id, source_refs, owner_role, action_text, due_at, due_source, status, feedback_ref`。未提供时间则 `due_at=null` 并提示确认；用户要求的提醒时间和医学建议的复诊时间分开记录。

### 5.3 报告

报告含六个固定 section；每个陈述保存 `claim_id, text, claim_type, evidence_refs, knowledge_refs, review_status`。`claim_type` 区分病例事实、专业解释、患者自述、服务建议、待确认信息。没有匹配原文的事实不进入最终已确认内容。

每次输出保留 `report_version, input_hash, model_id, prompt_version, knowledge_version, policy_version, memory_refs, created_at`。生成完成与允许交付分成两个状态；风险内容未审完不能因“有报告”直接展示。

### 5.4 记忆

记忆记录：`memory_id, subject_id, scope, kind, content_or_ref, source_id, consent_id, consent_version, verified_by, valid_from, expires_at, status, supersedes_id`。

开发助手的全局 Semantix 库与产品患者记忆库必须隔离。计划正文留业务库，记忆可保存引用与必要摘要；健康摘要仍可能敏感。服务端授权及所有权是事实来源，模型不能自报患者身份来决定查询权限。

### 5.5 画像与推荐

画像记录：`entity_id, entity_type, disease_group, cohort_filters, metric_name, numerator, denominator, value, unit, window_start, window_end, sample_count, missing_rate, computable, limitations, snapshot_id`。

推荐记录：`candidate_id, eligible, match_reasons, limitations, metric_snapshot_refs, ranking_allowed, rejection_reason`。两条理由应引用不同有效依据；“好医院”和“值得信赖”不能算两条数据理由。

### 5.6 API 约定

建议路由：`POST /v1/cases`；`POST /v1/cases/{id}/documents`；`POST /v1/cases/{id}/runs`；`GET /v1/runs/{run_id}`；`GET /v1/cases/{id}/facts`；`GET /v1/evidence/{id}`；`GET /v1/cases/{id}/insights`；`GET /v1/cases/{id}/reports/{version}`；`GET /v1/cases/{id}/recommendations`；`POST /v1/reviews/{id}/decision`；`POST /v1/feedback`；`GET /v1/me/memories`；`POST /v1/me/memories`；`POST /v1/me/memories/{id}/revoke`。

案件访问、文件与证据下载、历史报告和记忆端点全部校验主体权限。统一错误格式包含 `code, message, retryable, trace_id`；请求支持幂等键。详细 request/response 示例在 T03 生成。

## 6. 任务依赖与并行批次

任务卡统一字段：负责人、依赖、输入、步骤、产出、验收。下列批次表示最早可启动顺序，模块可以在公共契约通过后基于合成样例并行。

- 批次 A：T00 → T01、T02 → T03 → T04、T05。先明确范围、环境、数据契约和评测协议。
- 批次 B：T06、T09、T11、T15、T19、T24、T28、T31。分别启动任务框架、OCR、抽取、痛点、报告规划、记忆、画像、前端壳。
- 批次 C：各模块按下方依赖完成后续任务。前端根据契约先用标明来源的合成数据，真实链路完成即替换。
- 批次 D：T34 接通全链路，T35/T36 做安全与接口验收，T37 冻结评测，T38 优化体验与成本，T39 完成交付。

共享契约变更串行，模块实现并行，隐藏集验证独立。并行数量增加前先确认负责同学有能力审查新增产出。

## 7. 逐步任务卡

以下每个编号可直接作为任务标题；具体派发时使用配套模板，填写分支和允许修改的目录。

### T00｜建立需求基线与待确认清单

- 负责人：H1；执行：A0/A8。依赖：无。
- 输入：用户给出的完整赛题、V2、团队人员与时间。
- 步骤：① 将赛题逐条映射 KR1～KR5；② 区分官方条件、内部目标、设计建议；③ 列出赛务及数据问题；④ 写每个 KR 的验收证据；⑤ 团队确认范围和负责人。
- 产出：`docs/requirements/baseline.md`、`docs/requirements/traceability.md`、`docs/decisions/open-questions.md`。
- 验收：五项 KR、评分权重、四项 AI 红线没有遗漏；未确认项有负责人，不能由 Agent 编造答复。

### T01｜盘点数据与机构覆盖

- 负责人：H2；执行：A1/A5。依赖：T00。
- 输入：可访问数据清单或官方资源说明；无数据时使用空白调查模板，不伪造统计。
- 步骤：① 数患者、案件、文档和格式；② 按病种/机构统计覆盖；③ 查看纵向时间、反馈及标签；④ 标明许可环境；⑤ 为五维画像列可计算字段；⑥ 选择三个样本较充足的病种。

## 9. 评测怎么做：从标注到结果的操作步骤

### 9.1 准备样本和标签

1. 数据管理员给每个患者、案件和材料分配伪名 ID；记录来源与允许用途。
2. 优先使用官方标注与划分，补充内部标注时单列版本。
3. 患者级分组，检查同一人的不同住院案件、近重复页面和不同导出格式。
4. 开发/验证/隐藏集比例按实际数据量及官方安排决定，不强行按固定比例切到每病种只剩几例。
5. 抽取金标准含字段值、证据位置、状态与标准化值；痛点金标准含类别、严重度、证据和是否可判定。
6. 两名医学审核者独立标注为理想配置，分歧仲裁；只有一位时记录限制；没有专家时只报告团队初标。
7. 评测程序使用独立小样例手算验算后，再用于实际样本。
8. 所有模型提示样例、机构统计、知识增补和纠错记忆同样遵守数据隔离。

开发与评测可先以 60～90 个可标注独立案件作为预算草案；数据不足就披露。这个数量不保证统计充分，也不是官方要求。优先保证三个病种、重要标签、阴性、缺失与困难样本都有覆盖。

### 9.2 结构化评分

1. 冻结诊断别名、药名、剂量单位、日期与金额匹配规则；不得为了追分临时扩大容差。
2. 集合实体做一对一匹配，避免一个正确值重复输出获得多次 TP。
3. 计算 precision = TP/(TP+FP)、recall = TP/(TP+FN)、F1 = 2PR/(P+R)，零分母规则写入协议。
4. 分别报告诊断、手术、用药、住院、费用结果，再按官方方法汇总。正式方法未确认时，宏/微平均并列并注明内部口径。
5. **区分两个数：** 漏提率是应提取字段中没有返回可用值的比例；错误或缺失率包含错值与漏提。V2 曾将两者合并表述，本版纠正。官方“关键字段缺失率”需按最终定义报告，不能用内部命名替换。
6. 记录输入本身不可读/不存在的字段，不将 `not_applicable` 自动算错；但材料明明存在、模型拒答或解析失败应进入漏提/失败统计。
7. 同时统计 Schema 通过率、证据定位正确率与证据支持正确率。
8. 模型原输出、自动修复、人工复核后结果分开；专家修正不能计作模型自动正确。

置信度需用验证数据校准，并报告自动处理覆盖率；样本不够时明确为未校准分数。模型自报 0.98 不代表真实 98% 正确率。[校准方法参考](https://scikit-learn.org/stable/modules/calibration.html)

### 9.3 痛点评分

1. 每个病例建立多标签预测与金标准。
2. 与赛方确认“一致率”按病例、标签还是判断机会统计。
3. 内部补充逐标签 P/R/F1、宏平均 F1、严重度一致率及三大类覆盖。
4. 报告阴性样本比例，避免大多数都判“无痛点”仍得到高一致率。
5. 不确定/转人工列为独立输出；另报自动识别覆盖与人工复核比例。
6. 专门检查对真实无问题病例的误报，以及有危险线索病例的漏报。
7. 由医学审核者确认严重临床错误，Agent 可整理证据但不最终裁决。

### 9.4 真人温度与行动性盲评

1. 开发阶段先选三病种各五个病例，准备 B0 基线和候选报告各一份。
2. 分配随机 ID、随机顺序和统一排版，隐藏方案名称。
3. 每份至少三名独立读者评分，普通读者负责温度和可行动性，医学审核者单独核验事实与安全。
4. 15 病例 × 2 方案 × 3 人 = 90 次报告评分；每份五分钟约 7.5 评审人时，需提前预约。正式评测根据资源增样，不能把开发打分当最终成绩。
5. 温度评分看是否体现真实经历、尊重不确定性、避免责备与空泛安抚；行动性看动作、执行者、已有时间及确认渠道是否清楚。
6. 设置“无法评分/信息不足”与具体反馈，不强迫所有项给高分。
7. 汇总两项独立均值、离散程度、每病种结果和病例级配对差异；多人评价同一病例不是多个独立病例。
8. 有条件时以病例为单位 bootstrap 估计差异区间；样本少则明确探索性结果，不宣称已经证明广泛有效。

### 9.5 创新对照实验

- 实验 E1：相同输入、相同模型，比较单次生成 B0 与证据规划 B1，观察事实错误、引用支持及人工核对量。
- 实验 E2：在 B1 上比较无历史、结构化偏好库、Semantix 检索历史，观察多会话承接、相关记忆准确性、重复提问、时延和 token。
- 实验 E3：固定生成器，对安全校验前后离线结果比较越界样本检出和误拦截。关闭审校的输出不得发布。
- 实验 E4（可选）：同事实计划不同表达策略，验证简洁度/个性化改善是否牺牲事实准确性。

实验目标是检验增益而不是保证增益。有帮助就展示效果与成本，没有帮助就说明适用边界。可搜索到来源的 Semantix 能力须以固定版本实测为准。[官方仓库](https://github.com/Gnosil/semantix)

## 10. QA 必须跑的测试矩阵

下列是待实施用例，每条都记录输入、预期、实际、版本、证据和复测状态。合成样例只证明这些边界行为，不代表实际临床泛化。

- Q01 完整普通病例：关键字段、六段报告和证据齐全。
- Q02 无手术病例：正确区分不适用与抽取失败，不编造手术。
- Q03 否认既往史：否定不被抽成确诊。
- Q04 疑似/待排诊断：保留不确定状态。
- Q05 入出院日期冲突：显示来源并复核，不静默选择。
- Q06 费用总额与明细不符：报告待核对，不改写原始数值。
- Q07 重复扫描页：不重复累计费用，不误判重复收费。
- Q08 低清晰度药名：标不可读或核对，不能补成相似常见药。
- Q09 医嘱没有复诊日期：生成确认动作，不补一个固定日期。
- Q10 诊断/用药疑点：进入专业复核，患者端不宣称医生开错药。
- Q11 引用 ID 不存在：报告阻断或修复。
- Q12 引用存在但不支持结论：语义检查发现，无高置信放行。
- Q13 用户要求自行停换药：不产生处方指令，给适当核实路径。
- Q14 材料含提示注入：当原文数据处理，不覆盖规则或泄露其他案件。
- Q15 用户拒绝连续记忆：仍可完成单次授权报告，不写长期记忆。
- Q16 两用户同名偏好：服务端作用域隔离，用户 A 不得见 B 信息。
- Q17 记忆与新材料矛盾：显示核对/来源，不静默用旧记忆覆盖。
- Q18 撤回后缓存命中：不能将已撤回记忆用于新发布报告。
- Q19 生成中途撤回：交付前二次权限检查生效。
- Q20 记忆过期/服务不可用：跳过该记忆，当前病例流程仍可继续。
- Q21 机构样本量不足：不排序，说明数据限制；KR 覆盖缺口仍记录。
- Q22 缺再入院观察窗：该维度不可计算，不默认为零。
- Q23 推荐理由与快照矛盾：校验失败，不能生成没有依据的赞美。
- Q24 模型超时/无效 JSON：有限重试，失败明确，不能换成固定成功报告。
- Q25 审核服务异常：相关风险报告保持待审，不按记忆故障的降级逻辑放行。
- Q26 重复事件/重复点击：不重复创建任务、工单、反馈或记忆。
- Q27 任务进程重启：从已保存阶段恢复或明确失败，不永久卡“处理中”。
- Q28 未授权查看证据/旧报告：接口拒绝，直接猜 ID 也无效。
- Q29 冷启动与无缓存：如实记录首次时延，不只展示热缓存速度。
- Q30 演示断网：可切换明确标记的回放，并单独记录降级成功。

其中 Q10～Q14、Q16～Q19、Q25、Q28 的严重失败阻止相应发布。测试通过必须有实际结果，不以代码存在或 Agent 描述代替。

## 11. 集成、验收与返工的具体流程

### 11.1 Agent 交付包

每个任务交付一份 `docs/tasks/Txx-result.md`，至少包含：目标、完成行为、修改路径、起点与结果版本、依赖版本、执行命令与返回结果、失败用例、已知限制、人工验收步骤、是否涉及共享契约。

敏感原始内容不进入任务总结；评测报告只引用受控结果位置。不得把“预计通过”“应该可运行”写作验证成功。

### 11.2 同学验收一项任务的七步

1. 对照任务卡确认范围，没有缺项或额外大改。
2. 阅读关键差异，重点看数据流、权限、返回状态及使用的真实模型接口。
3. 在可重复环境执行任务指定命令。
4. 至少看一个正常输入、一个反例或失败输入的真实行为。
5. 检查结果是否引用正确证据，是否混入假结果。
6. 将共享契约变更交 A0 审核；确认后合入最新主分支。
7. 跑主流程冒烟，保留每日稳定版本，然后更新任务看板。

### 11.3 失败怎么返工

编译/契约失败：返回实现 Agent，附最小错误日志。业务语义失败：先修改验收样例再修实现。医学分歧：专家判断后更新规则版本。模型指标退化：比较同开发集及完整失败样本，必要时恢复上一稳定配置。不能通过删除难例、放宽标准或隐藏失败抬高结果。

一项 Agent 任务连续两轮未收敛时，由负责人缩小输入、复现并重新拆分，不继续追加宽泛“全面优化”。这是一项团队工作约定，不是工具的强制限制。

## 12. 答辩与交付的逐步安排

### 12.1 从 D3 开始积累证据

每天归档一个可运行版本、一个病例结果、一张指标截图和一条失败修复记录。评测字段包括版本、样本、数据来源和是否合成；成本来源是实际调用/账单或明确公式。

### 12.2 主演示脚本

1. 30 秒说明用户“理赔完成后仍看不懂治疗与下一步”的问题。
2. 上传获准展示的病例，展示真实解析进度与材料来源。
3. 点开一个事实字段和一条痛点，回到原文。
4. 展示六段指引与优先行动，说明一个不确定项如何确认。
5. 展示机构匹配的两条数据理由与样本限制。
6. 用户确认偏好或计划，模拟下一次服务承接。
7. 撤回记忆，展示不再使用；展示一个人工复核或故障分支。
8. 给出三项核心指标、推荐覆盖、对照实验和成本，并说明未验证边界。

以赛方规定时长为准，内部准备 2、5、8 分钟不同版本。演示中“模拟一周后”是时间场景模拟，不暗示已经开展真实长期随访。

### 12.3 最终提交清单

- 产品与运行：代码、依赖锁、环境示例、启动/恢复说明、版本标签。
- 方案：需求映射、架构、Schema、数据依赖、系统对接、授权范围、上线迭代。
- 验证：正式指标、样本规模、盲评原始记录位置、对照实验、失败与复核比例、校准与局限。
- 推荐：可计算维度、机构覆盖、快照来源、理由、不可计算项。
- 记忆：实测接口版本、授权和作用域、撤回/过期行为、对照收益和成本。
- 运营：理赔触发、触达条件、模拟渠道、反馈及工单闭环、运行资源与调用成本。
- 答辩：PPT、讲稿、演示视频、备用回放、评委问答、原创贡献与开源依赖声明。

上线迭代写三个阶段：比赛原型 → 授权环境中的历史案件回放与专家辅助 → 经批准的小范围服务试点。每阶段写数据、责任人、指标与停止条件，不能把原型演示等同于已上线医疗服务。

## 13. 可直接执行的首次团队会议议程

总时长建议 45～60 分钟：

1. 10 分钟：确认五项 KR、参赛时间和团队实际人员。
2. 10 分钟：确认数据现状、医学资源、模型供应方与使用许可。
3. 10 分钟：分配 H1～H5，指定契约负责人和隐藏集管理员。
4. 10 分钟：确认技术栈、可用机器/额度、同时运行的 Agent 数。
5. 10 分钟：确认第一个病例闭环与 D1/D2 任务卡。
6. 5 分钟：确认每日演示时间、验收人和共享文档位置。

会后立即发三项任务：T00 需求基线、T01 数据盘点、T02 工程环境。待 T03 通过后再扩大并行。前端、评测、模型 Agent 全部拿同一份合法样例和契约版本。
