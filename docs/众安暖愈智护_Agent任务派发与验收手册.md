# 众安·暖愈智护：Agent 任务派发与验收手册

> 与《Agent 协同开发详细执行方案 V3》配套使用。以下是可复制的任务文本，复制前替换尖括号占位项。
> 这些模板约束一次开发任务，不授予生产部署、外部发送、真实医疗数据上传或隐藏集读取权限。

## 1. 派发前，负责同学先做这六步

1. 从 V3 第 7 节选一张任务卡，例如 T11。
2. 确认依赖任务已验收，或明确只能用哪个契约样例开发。
3. 给 Agent 独立分支和工作目录，记录主分支起点提交。
4. 指明本次可修改目录、不可修改的共享文件和数据访问范围。
5. 写出至少一个正常例和一个反例的预期行为。
6. 约定验收人和结果报告路径，然后发送“通用任务模板 + 对应任务卡”。

首次只派 T00、T01、T02；T01/T02 可以在 T00 已确认的需求范围内准备。T03 完成后再按依赖扩大并行。任务状态由同学确认，不能让所有 Agent 同时改一个任务总表。

## 3. 首批任务：直接复制的三个起始指令

### 3.1 给需求与评测协调 Agent：T00

```text
请完成“众安·暖愈智护”任务 T00：建立需求基线。
阅读 docs/众安暖愈智护_Agent协同开发详细执行方案_V3.md。
依据当前提供的官方命题文本，不自行补充赛事规则。

请按顺序：
1. 将 KR1～KR5 拆成可检查的要求。
2. 每条要求注明官方阈值、内部目标、数据依赖和验收证据。
3. 单列 AI 原生度红线、数据真实性与完整链路要求。
4. 列出必须向赛方确认的指标口径、截止、数据许可与接口资源。
5. 写出原型范围与增强范围，给每项指定建议负责人角色。

仅修改 docs/requirements/、docs/decisions/open-questions.md 和本任务报告。
输出 baseline.md、traceability.md、open-questions.md、docs/tasks/T00-result.md。
每条 KR 必须能映射到后续任务和验收方法。
缺失信息标待确认，不填推测答案。不开始开发应用代码。
```

### 3.2 给数据 Agent：T01

```text
请完成任务 T01：盘点本项目实际数据与机构覆盖。
阅读 V3 的数据依赖、契约和 T01/T28。
只访问负责人提供的授权数据目录；未提供目录时创建调查模板并明确待验证。

请按顺序：
1. 统计实际材料类型、病例/患者/病种/机构覆盖和已有标签。
2. 检查是否有患者追踪、费用分类、反馈和完整观察窗口。
3. 将每个推荐维度映射到所需字段与公式。
4. 给出三个病种候选的证据和缺口。
5. 标明开发、评测、对外展示各自允许的使用范围。

输出 docs/data/inventory.md、coverage.md、permissions.md 和 T01-result.md。
统计程序只输出聚合信息，结果不包含姓名、联系方式或病历正文。
没有数据时不得生成看似真实的覆盖数量。
合成机构可以用于接口验证，但不能写成官方 KR4 已达标。
```

### 3.3 给工程 Agent：T02

```text
请完成任务 T02：搭建可重复运行的工程基础。
先检查当前仓库、分支、远程及未提交文件，保留已有文档和用户改动。
阅读 V3 的第 4 节目录与命令约定。

默认采用 React + TypeScript、FastAPI + Pydantic、PostgreSQL；
若已有明确实现栈，先报告差异并沿用已确定栈，避免无必要重建。

请按顺序：
1. 建立前后端工程、依赖锁和不含凭证的环境示例。
2. 建隔离的开发/测试配置，提供健康检查。
3. 创建 scripts/doctor.ps1、dev.ps1、check.ps1、evaluate.ps1 的命令接口。
4. 对尚无实现的 scope 明确返回“未实现”与非零退出码，不能默认成功。
5. 建基础 CI：格式/类型/有效测试；不在 CI 使用真实患者数据。
6. 写清新环境启动、关闭和故障排查步骤。

共享依赖和根配置由本任务统一维护。
不实现医疗模块，不生成虚构指标，不部署到生产或替团队提交比赛。
交付运行证据与 docs/tasks/T02-result.md。
```

## 4. 角色专用补充指令

以下内容附在通用任务模板后，不能代替任务卡的具体范围。

### 4.1 契约 Agent

```text
你维护共享契约唯一源。先写正常、缺失、冲突、失败样例，再实现 Schema。
字段需区分原文观察、推导、缺失、不可读、不适用和冲突。
时间精度、金额单位、证据坐标、主体标识和版本必须明确。
导出 JSON Schema/OpenAPI 与前端类型，记录生成方式。
不与其他 Agent 同时修改契约和数据库迁移。
改变既有字段需给兼容计划与消费方列表，不静默破坏接口。
```

### 4.2 文档理解 Agent

```text
你负责医疗材料解析与结构化。先保证字段和证据正确，再优化召回。
保留否定、疑似、既往/当前、文档来源和日期精度。
原始值与归一值都保留；不可读和跨文档冲突不能静默改成猜测值。
不依赖文件名或病例 ID 硬编码诊断。
用提供的开发样例和独立反例测试；不读取隐藏标签。
最后给字段误差分类、真实运行结果和未解决的版式问题。
```

### 4.3 痛点与温度 Agent

```text
你负责有证据的疑点识别和六段关怀报告。
对每个痛点检查类别、证据、严重度、动作与是否需要专业复核。
材料未写明不等于医生未执行；统计费用偏离不等于不合理收费。
生成分事实计划、表达和检查阶段，当前材料、知识、自述、历史记忆分别标来源。
每个事实陈述需能回到证据；资料不足时给确认动作，不新增医疗日期或处方。
不要通过给所有样本相同关怀模板或固定 4.5 分完成任务。
真人温度评分和医学审核留给相应评审者。
```

### 4.4 Semantix Agent

```text
你负责产品侧 MemoryAdapter。先验证固定版本真实接口，不假设医疗多租户能力。
使用独立业务测试库，严禁使用开发助手的全局 Semantix 用户库保存病例信息。
用户身份从服务端认证取得；元数据、授权和撤回状态由业务数据库控制。
写入需有确认来源，检索前限制作用域，注入和交付前再次核验。
实现过期、更正、撤回与缓存失效，并测试生成中途撤回。
分别记录停止使用、索引删除、物理副本清理的状态。
任何能力未被内核提供时，明确由适配层实现或记录缺口。
使用虚拟主体测试串用、超时、未授权和冲突。
```

### 4.5 画像推荐 Agent

```text
你负责有数据依据的机构/医生/方案画像和匹配。
先证明每维可计算，再实现评分；保存分子、分母、窗口、分层、样本数和快照。
无完整追踪不能计算再入院率；代理指标不能改名成临床质量。
每条理由需来自实际快照和患者当前需求，不让 LLM自由生成机构口碑。
缺失值不默认为零，也不补成平均值后隐藏缺失。
数据不足允许不给排名，同时报告 KR4 覆盖缺口。
合成数据只用于实现验证，正式指标与真实数据分开。
```

### 4.6 前端 Agent

```text
你负责让患者与审核人员清楚地使用已经定义的能力。
只调用已批准接口，不在前端写医疗结论或虚构指标。
页面必须处理加载、失败、缺失、冲突、待审核、无推荐和记忆不可用。
Mock 或回放模式明显标记，真实接口失败不能偷偷替换成成功样例。
证据跳转、反馈、撤回、复核按钮必须真实执行并显示后端确认结果。
权限由后端执行，前端隐藏按钮不能替代授权。
简洁/详细切换不改变事实；窗口切换不能残留其他患者数据。
交付关键交互截图或录屏，并说明实际访问的接口版本。
```

## 5. 独立评审 Agent 指令

```text
你是本任务的独立评审者。请审查 <Txx> 的代码与交付证据。
需求依据：<V3 对应任务卡>。
比较范围：<实际起点提交> 到 <实际结果提交>。

先检查：
1. 是否按契约实现了要求，有无共享接口漂移。
2. 是否存在硬编码成功结果、固定指标、失败样本丢失。
3. 当前用户是否可能访问别人的案件、证据、报告或记忆。
4. 缺失与临床不确定性是否被错误包装为确定结论。
5. 测试是否真正覆盖需求及反例，还是只重复实现逻辑。
6. 任务报告中的“通过”能否由实际日志或复跑支持。

只报告可复现的具体问题，注明触发条件、影响、文件位置和修复方向。
按阻断发布、重要功能缺陷、可延后问题分类。
不要因为缺少非本任务范围的生产级功能而否决两周原型。
未经另行任务安排不直接改代码、不改金标准、不访问隐藏标签。
输出 docs/reviews/<Txx>-review.md，结论为通过、需修改或因缺证据无法判断。
```

## 6. 集成 Agent 指令

```text
请把已验收的任务 <编号列表> 集成到最新稳定基线。
先检查当前工作树与团队未提交改动，不覆盖用户修改。

按顺序：
1. 核对每个任务的验收结论、起点版本和共享契约版本。
2. 识别相同文件、迁移编号、锁文件和 Schema 冲突。
3. 按依赖顺序合入，一次只处理可清楚验证的变更。
4. 契约冲突先解决语义再改代码，不能机械选择一侧。
5. 跑类型/模块/契约与受影响集成检查。
6. 用一个正常病例和一个失败病例走主流程。
7. 记录最终提交、通过检查、未解决问题和启动步骤。

不要为了通过测试删除失败用例或放宽验收。
不在本任务读取/改写隐藏评测数据。
结果写 docs/reviews/integration-<实际日期或版本>.md。
```

## 8. 正式评测执行指令

此任务只由评测管理员在受控环境派发；开发 Agent 不应获得隐藏输入与答案。

```text
执行冻结版本的评测，不进行模型开发或提示修改。
候选 manifest：<固定文件>。
评测协议：docs/evaluation/protocol.md。
输入/标签位置：<管理员提供的受控路径>。
输出位置：<受控结果目录>。

1. 校验代码、模型、提示、知识、索引和策略版本。
2. 核验患者级分组与去重记录。
3. 执行固定数据集，保留失败、超时、重试与转人工。
4. 分别计算原始自动输出与人工修正后的结果。
5. 输出分字段、分病种、分标签及总体指标与分母。
6. 只导出批准范围的聚合结果，隐藏答案不复制到开发库或记忆库。
7. 不根据观察到的答案修改候选配置再重跑称为独立评测。
8. 报告来源、版本、样本规模、未测项及局限。
```

## 10. 团队每天怎么派下一批任务

1. 查看未验收产出；优先把已有工作合并成可运行结果。
2. 查看被阻塞任务；先解决其唯一关键依赖。
3. 从依赖已满足的任务里选最影响五项 KR 的三至四项。
4. 为每项明确可写目录与一个人类验收人。
5. 派发通用模板和任务卡；Agent 开始前核对输入版本。
6. 同步会只讨论结果、阻塞和决策，不轮流朗读长日志。
7. 晚间至少走一遍主流程，更新 KR 状态和明日任务。

当 Agent 产出速度超过团队审核速度，应减少新开任务。把并行带来的时间用于真实验证、用户体验和答辩证据，避免在多个无法集成的分支上积累功能。
