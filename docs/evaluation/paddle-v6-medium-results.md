# PP-OCRv6 medium：七页实际对照结果

## 结论

v6 medium最长边960配置的最终字段F1为 **0.7332**，高于同一v50抽取口径下的v5 GPU960基线 **0.7115**，提高 **2.17个百分点**。OCR与字段抽取均7/7完成。它值得扩大验证，但尚未达到KR1的0.90，不代表全量、独立或官方达标。

官方默认分辨率配置在本机只成功3/7页，保留全部失败后F1为0.5278，暂不选用。应用默认仍为v5，没有自动切换或公网部署。

## 固定条件

相同七页开发原图、方向、修订金标v3、227个评分原子和`document-fee-taxonomy-exact-v5`。GLM-5.3-Flash、v50提示词、vision开启、bbox布局、两并发均相同。新旧预测记录的抽取实现摘要一致；没有改金标、评分器或加入表格模型。

v5基线复用上一轮`hybrid-v50-control7-*`，明确不是本轮新鲜调用。v6两组均新鲜识别原图后重新调用GLM。模型调用可能波动，七页不能建立稳定的泛化优势。

## 耗时与运行情况

- v5基线七页原生OCR合计5.420秒，中位0.703秒。
- v6 GPU960合计6.218秒，中位0.781秒。
- 默认分辨率3个成功页合计5.296秒，中位1.437秒；不含失败代价，不能据此声称总流程更快。

这些OCR时间不含首次模型加载、HTTP完整链路和GLM抽取。960组没有显示速度优势，主要收益是本轮字段分数。

环境复用本机Paddle3.2.2 GPU/CUDA12.6、PaddleOCR3.7.0、PaddleX3.7.2，RTX4060 Laptop 8GiB、驱动566.07。实际加载`PP-OCRv6_medium_det`及`PP-OCRv6_medium_rec`，不是只升级软件包仍加载v5。模型来自官方文档链接，下载来源、归档大小和SHA保存在模型目录的`download-provenance.json`。

默认分辨率使用最短边64、最大边4000，在运行中出现4页服务识别失败，并观察到NVIDIA驱动查询暂时不可用；停止该组后查询恢复。日志同时存在Paddle编译cuDNN9.9与运行9.5的警告。尚未确认失败根因，不能断言是显存不足或某个警告造成，也不能把失败直接当作模型精度问题。本轮没有更新显卡驱动或覆盖既有环境。驱动查询恢复后额外识别同一首张真实原图，960服务成功返回70个文字框、耗时0.969秒；该运行诊断保存在`paddle-v6-960-after-driver-recovery.json`，不替换固定评测缓存、不计为新增评测页。

## 复现资料与代码

方法和命令见[实验协议](paddle-v6-medium-experiment.md)。`--ocr-model v6_medium`和`ZHONGAN_PADDLE_OCR_MODEL=v6_medium`显式选择模型，两种分辨率独立parser版本，拒绝混用缓存和服务版本。v5默认行为保留。

仓库外`../preliminary-private/`包含：

- `paddle-v6-960-ocr7/`、`paddle-v6-64-ocr7/`及各自`-frozen7.json`。
- `paddle-v6-960-v50-*`、`paddle-v6-64-v50-*`的逐页预测、运行记录、分数和日志。
- `paddle-v6-final-comparison.json`：完整对照。
- `paddle-v6-v5-auxiliary.json`、`paddle-v6-v6_960-auxiliary.json`：逐页分数及名称字面命中。
- 高分辨率失败记录和服务日志，没有删除失败材料。

不新增、修改或主动运行测试，不校验原图哈希。所有医疗数据、权重、凭据、原生环境及私密配置留在Git仓库外。
